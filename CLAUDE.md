# Shakespeare Academy — contexte projet

Document de référence complet : `docs/Shakespeare_Academy_Cahier_de_Cadrage_v1.0.docx`.
**En cas de doute ou de divergence, ce cahier de cadrage fait foi — pas cette page, qui n'en est qu'un résumé opérationnel.**
Décisions métier encore non validées par l'école : `DECISIONS_PENDING.md` — ne jamais inventer une valeur pour un point qui y figure comme `OUVERT`.

## Doctrine

Critère central de réussite : sécuriser toute la chaîne de l'inscription à la clôture journalière, avec une traçabilité financière totale. Une opération financière validée n'est **jamais** modifiée ni supprimée : toute correction passe par une annulation contrôlée et une contre-écriture (RG09, RG18).

Avant d'ajouter une fonctionnalité, se demander : *est-elle nécessaire pour sécuriser l'inscription, la facturation, l'encaissement ou la clôture d'un élève, sans ressaisie ni incohérence ?* Si non, elle n'est pas prioritaire (cf. §1.2 du cadrage, hors périmètre initial : notes, emplois du temps, cantine, transport, paie, portail parent, mobile money, appli mobile).

## Règles non négociables (voir cadrage §5 pour le détail complet)

- **RG01** — Un élève a un matricule permanent et une seule inscription active par année scolaire.
- **RG02** — Une classe appartient à un niveau, une section et une année scolaire.
- **RG03** — Les frais sont versionnés par année scolaire ; modifier un tarif ne modifie jamais les factures déjà émises.
- **RG08** — Un trop-perçu est interdit (sauf compte d'avance explicitement activé — non activé au MVP).
- **RG09** — Une transaction validée est immuable. L'annulation crée une transaction inverse liée à l'originale.
- **RG10** — Les numéros de reçu sont uniques, séquentiels et générés côté serveur.
- **RG13** — La solvabilité est **calculée**, jamais saisie manuellement.
- **RG15** — Toutes les actions sensibles sont journalisées (utilisateur, horodatage, ancienne/nouvelle valeur) — voir `AuditService` (`apps/api/src/audit/`), append-only par conception.
- **RG16** — Les montants XAF sont des entiers, aucun calcul financier en flottant.
- **RG18** — Aucune suppression physique d'élève, inscription, facture ou transaction en production.
- **Permissions fines, jamais par rôle seul** (§3, §14) : chaque action sensible est gardée par une permission précise (`@RequirePermission('CODE')`), vérifiée côté serveur même pour un appel API direct — masquer un bouton côté client n'est jamais une sécurité.
- **Le Secrétaire-caissier ne valide jamais ses propres annulations, remises exceptionnelles ou écarts de caisse** — seule la Direction approuve (à construire au Lot 4).

## Stack

Next.js (apps/web, scaffoldé — aucune page métier encore construite, le Lot 1 est backend uniquement, comme l'a été le socle multi-tenant d'Elyon) · NestJS 11 (apps/api) · PostgreSQL 16 / Prisma 6.19.3 (apps/api/prisma/schema.prisma) · Docker Compose (Postgres dev + test uniquement pour l'instant).

**Choix de version Prisma délibéré** : Prisma 7/8-rc introduisent une rupture majeure (plus d'URL dans `schema.prisma`, adapters obligatoires, `prisma.config.ts`) — jugée trop récente et complexe pour ce socle. Rester sur Prisma 6.x (LTS stable) tant qu'une raison concrète n'impose pas la migration.
**`@nestjs/config` et `@nestjs/jwt` fixés en version pré-ESM** (`4.0.4` et `11.0.2` respectivement, `--save-exact`) : leurs versions plus récentes (12.x) publient du pur ESM, incompatible avec la transformation CommonJS de `ts-jest` utilisée par la suite e2e (`Must use import to load ES Module`). Revoir seulement si toute la chaîne de test bascule vers un runner nativement ESM.

## État actuel du scaffold

- **Lot 1 (socle) fait et vérifié** : `apps/api` compile (`npm run build`), démarre (`npm run start:dev`) et sert du trafic réel — vérifié manuellement via `curl` (login réel, création de section réelle, token JWT valide) en plus des tests automatisés.
- `apps/api/prisma/schema.prisma` : uniquement les entités du Lot 1 — `School`, `AcademicYear`, `Section`/`Cycle`/`Level`/`Class`, `User`/`Role`/`Permission`/`RolePermission`, `RefreshToken`, `AuditLog`. Les entités de facturation/paiement/caisse (Lots 3-5) sont **volontairement absentes** : plusieurs règles dont elles dépendent restent `OUVERT` dans `DECISIONS_PENDING.md` (granularité des remises, gestion du trop-perçu, etc.) — les modéliser maintenant risquerait de figer une hypothèse fausse.
- **Mono-établissement, pas multi-tenant** : une seule ligne `School` existe. `schoolId` est présent sur les entités scopées (anticipation d'une extension multi-site future, cadrage §11) mais aucun mécanisme de sélection de tenant n'est construit — `SchoolService.getDefaultId()` (`apps/api/src/school/`) résout systématiquement l'unique établissement. Ne pas confondre avec le modèle multi-tenant d'Elyon (autre projet, header `x-tenant-id`) : ici, il n'y a qu'un seul restaurant... pardon, une seule école.
- **Auth** (`apps/api/src/auth/`) : JWT d'accès court (15 min par défaut, `JWT_ACCESS_TTL`) signé et vérifié côté serveur à chaque requête (`JwtAuthGuard` recharge l'utilisateur + permissions depuis la base à chaque appel, jamais depuis le payload du jeton — un compte désactivé ou un rôle modifié a un effet immédiat). Rafraîchissement via cookie `httpOnly` (`refresh_token`, scope `path=/auth`), rotation à chaque `POST /auth/refresh` (l'ancien jeton est révoqué). Mots de passe hachés Argon2id. Verrouillage après 5 échecs consécutifs (15 min, `MAX_TENTATIVES_CONNEXION`/`DUREE_VERROUILLAGE_MINUTES` dans `auth.service.ts` — décision technique de sécurité, pas une règle métier de l'école, donc non listée dans `DECISIONS_PENDING.md`). Récupération administrée (`PATCH /users/:id/reset-password`, `USER_MANAGE`) : jamais d'auto-inscription ni de lien de réinitialisation par e-mail.
- **Permissions** (`apps/api/src/roles/`) : catalogue de 6 permissions Lot 1 (`SETTINGS_MANAGE`, `USER_MANAGE`, `ROLE_MANAGE`, `ACADEMIC_YEAR_MANAGE`, `ACADEMIC_STRUCTURE_MANAGE`, `AUDIT_LOG_READ`) — **volontairement incomplet** : les codes cités en exemple par le cadrage §3 (`PAYMENT_CREATE`, `PAYMENT_CANCEL_APPROVE`, `CASH_CLOSE`, `EXPENSE_CREATE`) seront ajoutés à `prisma/seed-data.ts` au fur et à mesure que leurs modules (Lots 3-5) seront construits, jamais avant qu'une route ne les vérifie réellement. 5 rôles seedés conformes au tableau du cadrage §3 (`ADMINISTRATEUR`, `DIRECTION`, `SECRETAIRE_CAISSIER`, `COMPTABLE`, `AUDITEUR`) — `SECRETAIRE_CAISSIER`/`COMPTABLE` n'ont encore aucune permission assignée (leur domaine n'existe pas avant les Lots 2-5). `GET /roles`/`GET /permissions` sont lisibles par tout utilisateur authentifié (nécessaire pour peupler un sélecteur de rôle) ; seules les mutations exigent `ROLE_MANAGE`.
- **Structure académique** (`apps/api/src/{sections,cycles,levels,classes}/`) : hiérarchie `Section → Cycle → Level → Class` conforme au modèle recommandé du cadrage §2. Lecture ouverte à tout utilisateur authentifié, écriture derrière `ACADEMIC_STRUCTURE_MANAGE`. `Class.serie`/`Class.groupe` : colonnes prévues par anticipation de la décision D02 (séries de lycée, sous-groupes), non exploitées tant qu'elle reste ouverte.
- **Années scolaires** (`apps/api/src/academic-years/`) : statuts `BROUILLON`/`ACTIVE`/`CLOTUREE`. Une seule année `ACTIVE` à la fois — **activer une nouvelle année échoue explicitement s'il en existe déjà une active** (jamais de bascule automatique silencieuse ; la Direction doit d'abord clôturer l'ancienne). Une année `CLOTUREE` ne peut plus être modifiée.
- **Audit** (`apps/api/src/audit/`) : `AuditService.log()` est **append-only par conception** (aucune méthode de mise à jour/suppression exposée). Sérialise automatiquement les valeurs Prisma (dates comprises) en JSON — jamais besoin de sérialiser soi-même côté appelant. Ne journalise **jamais** un hash de mot de passe, ni avant ni après une réinitialisation. `GET /audit-logs` derrière `AUDIT_LOG_READ`, filtrable par utilisateur/entité/période.
- **Établissement** (`apps/api/src/school/`) : `GET /school` public à tout utilisateur connecté, `PATCH /school` derrière `SETTINGS_MANAGE`. `devise`/`fuseauHoraire` fixés par les exigences non fonctionnelles du cadrage (XAF, Africa/Brazzaville) — pas exposés en modification tant qu'aucun besoin réel de les changer n'apparaît.
- **Tests** : 39 tests e2e (Jest + Supertest, `apps/api/test/*.e2e-spec.ts`) contre une base Postgres dédiée (`shakespeare_academy_test`, jamais la base de dev) — auth (login/lockout/refresh/logout/changement de mot de passe), permissions fines (CA14 : refus serveur direct sans la permission requise), années scolaires (règle d'unicité de l'année active), structure académique (hiérarchie, doublons, filtres), utilisateurs (création/désactivation/réinitialisation), rôles/permissions (catalogue, assignation), audit (journalisation, jamais de hash), établissement. **Suite e2e exécutée avec `--runInBand`** (obligatoire : plusieurs fichiers de test partagent la même base dédiée, une exécution parallèle provoque des collisions de clés uniques/FK entre suites). Fixtures partagées : `prisma/seed-data.ts` (référentiel rôles/permissions/admin, réutilisé par le vrai script de seed **et** par les tests, pour ne jamais faire diverger les deux) + `test/utils/` (`test-app.ts`, `clean-database.ts`, `fixtures.ts`).
- **Seed** (`apps/api/prisma/seed.ts`, `npm run db:seed`) : idempotent, crée l'établissement (nom par défaut "Shakespeare Academy", à corriger via `PATCH /school` avec le vrai nom/adresse une fois connus), les 5 rôles, les 6 permissions Lot 1, et un compte `ADMINISTRATEUR` (`admin@shakespeareacademy.cg` / `ChangeMe123!` par défaut, **à changer immédiatement en production** — `doitChangerMotDePasse: true` dès la création, `ADMIN_SEED_EMAIL`/`ADMIN_SEED_PASSWORD` pour surcharger).
- **Lot 2 (élèves, responsables, inscriptions) fait et vérifié** : mêmes garanties que le Lot 1 (build/lint propres, e2e verts, vérification manuelle réelle via `curl`).
- `NumberSequence` (`apps/api/src/common/number-sequence.service.ts`) : séquence atomique générique (`schoolId`, `type`, `scope`), un seul `upsert` (INSERT ... ON CONFLICT côté Postgres) donc atomique sous accès concurrent sans verrou explicite. Utilisée pour le matricule (`type: 'MATRICULE'`, `scope` vide — permanent, D32) et le numéro d'inscription (`type: 'ENROLLMENT'`, `scope: academicYearId` — par année). Réutilisable telle quelle pour les numéros de reçu/pièce du Lot 4 (RG10).
- **Matricule** : généré automatiquement si non fourni, format `000001` (6 chiffres, sans année — D32 corrigé en cours de Lot 2 : un premier brouillon de `DECISIONS_PENDING.md` proposait un format incluant l'année, qui aurait contredit la permanence du matricule déjà actée dans la même section). **Numéro d'inscription** : `{libellé année}-{5 chiffres}` (ex. `2026-2027-00001`), par année — jamais confondu avec le matricule, qui lui ne change jamais.
- **Élèves/responsables** (`apps/api/src/students/`) : `POST /students` crée l'élève et son premier responsable dans une même transaction Prisma (cadrage §12), conforme au parcours §4.1. Un responsable est retrouvé-ou-créé par téléphone au sein de l'établissement (`Guardian.@@unique([schoolId, telephone])`, même patron R9 qu'Elyon) — un même parent n'est jamais dupliqué pour un deuxième enfant. `POST /students/:id/guardians`/`PATCH /students/guardians/:id`/`DELETE /students/:id/guardians/:guardianId` gèrent les responsables au-delà de la création initiale (fratrie, tuteur additionnel) — le lien `StudentGuardian` peut être détaché sans que RG18 s'applique (ce n'est ni un élève, ni une inscription, ni une facture, ni une transaction).
- **D33 (détection de doublon) implémentée** : `POST /students` compare nom+prénom+date de naissance normalisés (accents/casse ignorés) aux élèves déjà connus. Une correspondance exacte renvoie 409 avec le doublon potentiel dans le corps de la réponse, sauf si `forcerCreation: true` est explicitement passé — alerte non bloquante, jamais un blocage définitif ni une fusion automatique (l'écran de fusion reste différé, comme documenté dans D33).
- **`GET /students/search`** (cadrage §4.1/§12) : matricule, nom/prénom (normalisés), téléphone d'un responsable, ou date de naissance exacte (format `AAAA-MM-JJ`).
- **Inscriptions/réinscriptions** (`apps/api/src/enrollments/`) : `POST /enrollments` couvre les deux cas du cadrage §4.1/§4.2 avec un seul endpoint — `type` (`INSCRIPTION`/`REINSCRIPTION`) est **toujours dérivé côté serveur** (REINSCRIPTION si l'élève a au moins une inscription antérieure, quel que soit son statut), jamais choisi par le client. RG01 (une seule inscription **active** par élève et par année) appliqué en application, pas en contrainte DB : une inscription annulée ne bloque pas une nouvelle inscription pour la même année (correction possible sans contrainte artificielle). Rejette une classe qui n'appartient pas à l'année scolaire indiquée (400) et toute inscription dans une année `CLOTUREE` (409). `POST /enrollments/:id/cancel` exige un motif, journalisé (RG15) — pas d'approbation Direction à ce stade (aucune facture n'y est encore rattachée, contrairement à une annulation de paiement au Lot 4).
- **Alerte impayés antérieurs (§4.2) volontairement absente** : elle suppose des factures/paiements qui n'existent pas avant le Lot 3/4. L'implémenter maintenant aurait exigé d'inventer une donnée financière — reportée telle quelle, sans placeholder trompeur (ex. toujours "aucun impayé").
- **Permissions Lot 2** : `STUDENT_READ` (lecture élèves/responsables/inscriptions — Administrateur, Direction, Secrétaire-caissier, Auditeur) et `ENROLLMENT_MANAGE` (création/modification élève, responsable, inscription, annulation — Administrateur, Secrétaire-caissier uniquement), une seule permission de gestion plutôt qu'une par sous-domaine (le cadrage §3 regroupe ces activités pour le même rôle). Comptable n'a accès à aucune des deux (son périmètre, sorties/rapports, arrive au Lot 5).
- **Tests** : 57 tests e2e au total (+18 pour le Lot 2 : création élève+responsable en transaction, matricules séquentiels, réutilisation d'un responsable partagé, D33 avec/sans `forcerCreation`, recherche, dossier élève, rattachement/détachement de responsable, permissions STUDENT_READ/ENROLLMENT_MANAGE, inscription/réinscription, RG01, classe hors année, année clôturée, annulation avec motif + audit, filtres).
- **Frontend des Lots 1 et 2 fait et vérifié manuellement dans le navigateur** (`apps/web`) : App Router, Tailwind, style inline via classes utilitaires (pas de bibliothèque de composants ajoutée). Aucune page pour les Lots 3-6 (factures, paiements, caisse, rapports) — n'existe pas encore côté backend.
- **Auth frontend** (`apps/web/lib/api.ts`, `apps/web/contexts/auth-context.tsx`) : le jeton d'accès ne vit **qu'en mémoire** (jamais `localStorage` ni cookie non-httpOnly), cohérent avec le choix côté API — au chargement de la page, un rafraîchissement silencieux via `POST /auth/refresh` (cookie httpOnly) restaure la session sans redemander le mot de passe. `api.ts` retente automatiquement une requête ayant reçu 401 après un rafraîchissement réussi ; sinon, redirige vers `/login`. `doitChangerMotDePasse` (renvoyé par `/auth/login`, pas par `/auth/me`) redirige vers `/changer-mot-de-passe` avant tout accès au tableau de bord.
- **Permissions côté client** : `useAuth().hasPermission(code)` masque des boutons/liens pour l'ergonomie uniquement (ex. nav "Utilisateurs & rôles" visible seulement avec `USER_MANAGE`) — **jamais un contrôle de sécurité**, le serveur revérifie systématiquement (§14, déjà appliqué côté API). Une page consultée sans la permission de mutation reste lisible avec ses champs désactivés plutôt que masquée entièrement (ex. `/parametres/etablissement` sans `SETTINGS_MANAGE`).
- **Écrans Lot 1** : connexion, changement de mot de passe forcé, tableau de bord (année active + effectif + raccourcis), établissement, années scolaires (création/activation/clôture), structure académique (Section→Cycle→Niveau→Classe en 4 colonnes avec sélection en cascade), utilisateurs & rôles (deux onglets : création/désactivation/réinitialisation de mot de passe ; permissions par rôle sous forme de pastilles cliquables), journal d'audit (liste filtrable par objet).
- **Écrans Lot 2** : liste élèves avec recherche (debounce 300ms sur `GET /students/search`), dossier élève (identité, responsables avec ajout/détachement, parcours annuel avec annulation d'inscription), et un **assistant d'inscription unique** (`/eleves/inscription`) couvrant à la fois la première inscription et la réinscription — reflète exactement la conception backend (`POST /enrollments` dérive `type` automatiquement) : onglet "Élève déjà connu" (recherche) vs "Nouvel élève" (formulaire avec responsable), puis sélection année/section/cycle/niveau/classe en cascade, puis confirmation. La détection de doublon (D33) y est gérée : un 409 avec `doublonPotentiel` affiche une alerte avec un bouton explicite « Ce n'est pas un doublon, créer quand même » (jamais un contournement silencieux).
- **Bug réel trouvé et corrigé en vérifiant dans le navigateur** : sur `/parametres/structure`, créer une classe renvoyait bien 201 côté serveur mais n'apparaissait pas dans la liste — `loadAll()` (rechargement après création) ne rafraîchissait jamais `classes`, qui dépend d'un `useEffect` séparé keyé sur `[selectedLevelId, selectedYearId]` (des valeurs inchangées par un simple ajout). Corrigé en extrayant `loadClasses()` et en l'appelant explicitement après chaque création, en plus de `loadAll()`.
- **Contrainte d'environnement de vérification (pas un bug du projet)** : dans cette session, le port 3000 par défaut du serveur de développement Next.js renvoyait une réponse HTML corrompue/mise en cache pour toutes les requêtes de chunks JS (`Uncaught SyntaxError: Unexpected token '<'`) au sein du navigateur intégré de l'outil — reproductible avec Turbopack et webpack, mais absent en `curl` direct depuis la machine, et absent après avoir changé le port du serveur web (3010). Cause isolée à l'infrastructure de la session d'outillage (probablement un cache de proxy propre à ce port dans cet environnement), pas au code : aucun changement de configuration n'a été fait dans le projet pour cette raison (le port 3000 reste la valeur par défaut normale de `next dev`).

## Déploiement production — académy.lobima.online (12 septembre 2026)

**Déployé et vérifié en conditions réelles** : `https://academy.lobima.online` (web) et `https://api-academy.lobima.online` (API), sur le **même VPS qu'Elyon** (autre projet du même opérateur, `elyon-restaurant-mvp`), à la demande explicite de l'utilisateur — pas un choix d'architecture pris seul.

- **Cohabitation avec Elyon sur un VPS partagé** : Shakespeare Academy vit dans son propre répertoire (`/docker/shakespeare-academy` sur le VPS) avec son propre `docker-compose.yml` (nom de projet `shakespeare-academy`, réseau `shakespeare-academy_default`, base Postgres dédiée `academy-db`) — **jamais géré par le `docker-compose.yml` d'Elyon**. Seuls `academy-api`/`academy-web` rejoignent *en plus* le réseau Docker d'Elyon (`elyon-restaurant-mvp_default`, déclaré `external: true`) pour être joignables par son Caddy déjà en place sur les ports 80/443 — aucun deuxième Caddy possible sur les mêmes ports.
- **Piège réel rencontré en déployant, pas anticipé** : `academy-db` s'appelait initialement `db` — mais Elyon a **aussi** un service nommé `db`. Un conteneur connecté à deux réseaux Docker où le même alias existe sur chacun résout ce nom de façon ambiguë : `academy-api` s'est retrouvé à résoudre "db" vers la base **d'Elyon** (échec d'authentification, mauvais réseau) plutôt que la sienne. Corrigé en renommant le service `db` → `academy-db` (jamais un nom générique pour un service qui vit sur un réseau partagé avec un autre projet).
- **Deux autres bugs réels trouvés et corrigés pendant ce déploiement** :
  1. Le point d'entrée du Dockerfile (`node dist/main.js`, copié du patron Elyon) était faux pour ce projet : `tsconfig.json` ne fixe pas `rootDir`, et la compilation couvre à la fois `src/` et `prisma/` (à cause de `seed.ts`) — tsc calcule alors une racine commune et préserve `src/` sous `dist/`. Le vrai point d'entrée est `dist/src/main.js`. Puisque `dist/prisma/seed.js` est lui aussi déjà compilé (mêmes dépendances `@prisma/client`/`argon2`, déjà en `dependencies` de production), la production peut lancer le seed via `node dist/prisma/seed.js` sans jamais avoir besoin de `ts-node` (resté en devDependency, absent de l'image de production).
  2. `docker-compose.yml` positionne les variables optionnelles à une chaîne vide (`${ADMIN_SEED_EMAIL:-}`) quand elles sont absentes de `.env.production` — jamais réellement *absentes* du `process.env` du conteneur. `seed-data.ts` utilisait `options.adminEmail ?? 'valeur par défaut'` : `??` ne se déclenche que sur `null`/`undefined`, jamais sur `''`. Un premier compte admin a donc été créé avec un email **et un mot de passe vides**, invisible tant que personne ne testait un vrai login. Corrigé dans `prisma/seed.ts` (`process.env.ADMIN_SEED_EMAIL || undefined`, jamais la valeur brute) — potentiellement le même piège pour toute variable optionnelle future lue via `??` plutôt que `||`.
- **Structure des fichiers Compose** : `docker-compose.yml` est sûr par défaut (aucun port publié sur `academy-db`, pas de montage lié aux tests e2e) — utilisable tel quel aussi bien en dev qu'en production. `docker-compose.override.yml.example` (copié en `docker-compose.override.yml`, gitignored) republie le port Postgres (`5544`) et monte `init-test-db.sql` **uniquement** pour le développement local — jamais présent sur le VPS. Même patron que `docker-compose.override.yml.example` côté Elyon.
- **Secrets** : `.env.production` (jamais commité, sur le VPS uniquement) contient `POSTGRES_PASSWORD`/`JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET` générés aléatoirement (`openssl rand -hex 32`), jamais des valeurs par défaut. Voir `.env.production.example` à la racine pour la liste complète.
- **Caddy** : deux blocs ajoutés à la suite du `Caddyfile` **d'Elyon** (`/docker/elyon-restaurant-mvp/Caddyfile` sur le VPS — fichier appartenant à l'autre projet, sauvegardé avant modification) pour `academy.lobima.online`/`api-academy.lobima.online`, appliqués par un **rechargement gracieux** (`caddy reload`, jamais un restart du conteneur) pour ne jamais interrompre le trafic Elyon en cours. Certificats Let's Encrypt de production obtenus et vérifiés (émetteur réel, pas auto-signé) dès que le DNS (deux enregistrements A vers `77.37.87.119`, ajoutés par l'utilisateur) a propagé.
- **Compte administrateur de production** : créé via `docker exec ... node dist/prisma/seed.js` puis son mot de passe changé immédiatement après la première connexion réelle (le mot de passe par défaut `ChangeMe123!` documenté dans ce fichier ne doit **jamais** rester actif sur un déploiement public) — nouveau mot de passe connu seulement de l'utilisateur.
- **Vérifié de bout en bout en conditions réelles** : DNS, HTTPS (certificat réel), CORS (`WEB_ORIGIN`), login réel, changement de mot de passe forcé, tableau de bord chargé — sans jamais interrompre Elyon (vérifié après coup : `app.lobima.online`/`api.lobima.online` toujours 200, tous les conteneurs Elyon toujours `healthy`/`Up`, aucun redémarrage de leurs conteneurs).
